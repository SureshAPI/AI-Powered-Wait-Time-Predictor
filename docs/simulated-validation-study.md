# Simulated Validation Study

> **SIMULATED / DEMONSTRATION DATA — NOT REAL USER TESTING.**
> Every persona below is hypothetical. Every number below is generated by
> `src/simulate_validation.py` (seeded, reproducible), not collected from a
> real person. See `docs/validation-approach.md` for the full rationale and
> what this does and does not demonstrate.

## Personas (all hypothetical)

| ID | Persona | Profile |
|---|---|---|
| P1 | Rushed Professional | Office worker on a lunch break, low patience, values speed over detail. |
| P2 | Budget-Conscious Student | College student, comfortable with apps, plans around class timing. |
| P3 | Cautious Parent | Handling a child's warranty claim, lower tech familiarity, wants reassurance. |
| P4 | Skeptical Repeat Customer | Has used the shop before with no prediction tool; doubts a system can estimate this well. |
| P5 | First-Time Warranty Claimant | Unfamiliar with the warranty process, wants terms explained clearly. |

## Task script (same as the real protocol in `docs/testing-protocol.md`)

Each simulated persona "performs": (1) enter a repair request, (2) review
the predicted range, (3) explain the result in their own words, (4) decide
whether they'd wait, (5) rate understandability, (6) give feedback.

## Reading these results (as a demonstration of analysis, not a real finding)

- The simulated Cautious Parent persona is the one "failed" task and gave
  the lowest trust/willingness scores — consistent with how that persona was
  defined (lower tech familiarity, wants reassurance). This shows the kind
  of segment a real study might flag as needing clearer UI copy or
  in-person explanation, **if** it turned up in real data.
- Trust (3.0/5 mean) is the lowest-scoring measure across personas, ahead of
  only itself — worth watching for in real testing, since low trust could
  reduce whether customers actually rely on the estimate.
- Ease of Use scored highest (4.2/5), suggesting the form itself is not a
  bottleneck — again, only within this simulated demonstration.

## What would change with real data

Real testing (using the identical protocol in `docs/testing-protocol.md`)
would replace every number above with actual observations, and this section
would be rewritten to report genuine findings, explicitly distinguished from
this simulated section rather than merged into it.
