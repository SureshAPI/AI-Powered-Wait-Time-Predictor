# AI-Powered Waiting Time Prediction for Mobile Repair and Warranty Services

**Project Better Tomorrow — Continuation Track (Pathway A)**
Continuation of *C29 – Design Thinking for AI-Powered Problem Solving*.

> Status: 🟢 Project Complete (100% Completion) — see [Current Status](#current-status).

## Problem

Customers at mobile/electronics repair and warranty service shops do not know how long
their repair or service will take. Wait time varies with repair type, phone brand/model,
reported issue, current workload, technician availability, warranty procedure, and parts
availability. This uncertainty interferes with customers' work, college, travel, and other
schedules.

This project originated from a real field visit conducted at a mobile/electronics repair
shop in Gandhipuram, Coimbatore, during the previous Design Thinking phase (Empathise →
Define). This continuation begins at **Ideate → Prototype → Validate → Deliver** — the
Empathise and Define stages are not being repeated.

## Proposed Solution

An AI-assisted system that takes job details (service type, phone brand/model, reported
issue, current workload, technician availability) and produces an **estimated service/
waiting-time range** — communicated explicitly as an estimate, never as a guarantee.

## Objectives

- Give customers a realistic waiting-time estimate before they decide to wait.
- Give employees a simple tool to enter job details and share an estimate.
- Demonstrate a technically honest AI/ML pipeline (baseline estimator + Gradient Boosting
  Regression) without overstating predictive power on limited data.
- Produce prototype evidence suitable for academic review, using a clearly
  labelled simulated validation study rather than claiming real user testing
  that was not conducted (see `docs/validation-approach.md`).

## Prototype

```bash
pip install -r requirements.txt
python src/generate_synthetic_data.py   # regenerate the synthetic dataset
python -m src.train                     # (optional) train baseline + GBR standalone, print metrics
python -m pytest tests/ -v              # run the automated tests

python app/app.py                       # run the prototype web app
# then open http://127.0.0.1:5000/
```

The app trains the model itself at startup (fast — 600 synthetic rows), so no
separate model file needs to be committed. Enter job details on the intake
form to see the estimated service-time range.

## Testing

Real user testing was **not conducted** for this project. Instead, this
project uses a clearly-labelled **simulated validation study** — hypothetical
tester personas and synthetic interaction data, generated by a documented,
seeded script, used to demonstrate the validation methodology and analysis
approach. See [`docs/validation-approach.md`](docs/validation-approach.md)
(rationale and what it does/doesn't show) and
[`docs/simulated-validation-study.md`](docs/simulated-validation-study.md)
(personas, results, analysis). The original real-testing protocol is
retained, unfilled, in [`docs/testing-protocol.md`](docs/testing-protocol.md)
in case real testing becomes possible later. **No claim anywhere in this
repository presents simulated results as real user feedback.**

## Current Status

**Phase 1 (Completed & Evaluated — 35% completion, 32.2/35 marks)**
- Problem context, continuation-track rationale, and architecture documented.
- Synthetic dataset schema and generator (600 rows).
- Baseline estimator and Gradient Boosting Regression (GBR) model with fixed ±20 min range.
- Prototype Flask web app: customer intake, departure-board result screen, CSV-based job log, and employee dashboard.
- Internal QA pass: clamped negative predictions, formatted readable hour/minute durations.
- Simulated validation study (5 hypothetical personas).
- Original visual identity: "service departure board" design theme.

**Phase 2 (Completed — Cumulative 70% completion)**
- **Enhanced Intake & Data Pipeline:** Separated `reported_issue` from `service_type` across 8 service categories with 38 specific symptoms and complexity multipliers. Added client-side dynamic selection cascade and comprehensive server-side input validation. Dataset expanded to 800 rows (`data/synthetic_service_data.csv`).
- **Data-Driven Prediction Intervals:** Replaced fixed ±20 min band with Quantile Gradient Boosting Regressors ($\alpha=0.10$ and $\alpha=0.90$) producing an 80% empirical prediction interval conditioned on job features.
- **SQLite Persistence & Safe Migration:** Replaced fragile CSV logging with SQLite (`data/jobs.db`). Implemented automatic, idempotent legacy CSV migration that marks historical records as `source='demo'` to preserve clean separation from real operational data.
- **Job Lifecycle & Status Management:** Introduced validated status state machine (`open` → `in_progress` → `completed` / `cancelled`, `cancelled` → `open`) with mandatory, positive actual-duration recording on completion.
- **Employee Dashboard & Live Analytics:** Added real-time text search and filters (status, service type). Implemented operational analytics (AI MAE, baseline MAE, mean error) that strictly query completed live records (`source='live'`) and require $N \ge 3$ to avoid misleading small-sample claims.
- **Prediction Explanations:** Created an interpretive feature contribution analyzer (`src/explanations.py`) comparing inputs to neutral training medians, generating concise customer status notes and detailed employee factor breakdowns without falsely claiming formal SHAP attribution.
- **Deployment & Testability:** Implemented Flask application factory (`create_app`), health monitoring endpoint (`/health`), Gunicorn WSGI compatibility (`gunicorn app.app:app`), and expanded automated test suite (17/17 tests passing in `tests/test_pipeline.py`).

**Phase 3 (Completed — Final 30%, Cumulative 100% Completion)**
- **Customer Self-Service Tracking & Service Timeline:** Added customer ticket lookup (`/track`) and real-time tracking interface (`/track/<job_id>`) with a 3-stage visual progress meter, device details, and chronological service timeline backed by an audit-ready `job_events` SQLite table.
- **Queue Workload Intelligence:** Integrated live queue analytics on the staff dashboard, displaying active shop load, total estimated backlog minutes, delayed repair counts, and high-variance job alerts.
- **Proactive Delay & Uncertainty Alerts:** Implemented runtime delay monitoring comparing elapsed time against predicted wait duration, providing staff and customers with immediate visibility when a repair runs past schedule. Prediction intervals flag high-uncertainty repairs (e.g. pending component ordering).
- **Staff Access Control:** Added workshop PIN protection (`/dashboard/login`) with session management, securing employee queue management, status updates, and reports while maintaining public customer ticket tracking.
- **Export & Print Utilities:** Built one-click printable estimate receipts via dedicated print media stylesheets (`@media print`) and added RFC-4180 CSV export (`/dashboard/export`) preserving active search and filter queries.
- **Design System & Error Handling:** Polished the signature "service departure board" aesthetic with wide desktop viewports (up to 960px), accessible contrast, custom 404/500 error pages, and 23 automated tests passing (100% coverage across ML and web flows).

## Limitations

- **Synthetic Training Data.** All model training remains on synthetic demonstration data (`data/synthetic_service_data.csv`). Real-world predictive accuracy cannot be claimed without genuine historical shop logs.
- **Simulated Validation.** The user validation study remains simulated (`docs/simulated-validation-study.md`) to reflect ethical academic honesty until field testing with real shop customers is conducted.
- **Single-Workshop Storage.** SQLite provides robust local persistence for an individual repair shop, but does not support multi-tenant distributed cloud deployments.

## Future Scope

- Integration with electronic point-of-sale (EPOS) or barcode scanning systems for automated ticket lookups.
- Automated retraining daemon triggered when live completed records exceed statistical threshold ($N \ge 100$).
- Field deployment study with real repair technicians at the Gandhipuram workshop.
